# RFP-Reviewer Skill 方案计划

## 1. 定位修正

当前要设计的不是面向终端用户点击使用的 SaaS 产品，而是面向 Agent 的 Skill。

Skill 的真实执行链路是：

```text
用户提交招标/投标/企业资料 -> Agent 判断触发 rfp-reviewer skill -> Skill 指导 Agent 调用工具和执行审查流程 -> Agent 输出风险报告、偏离表、补料清单、应标建议
```

因此，方案主线应从“用户如何使用产品”调整为“Agent 如何可靠、可审计、可复核地执行招投标合规预审”。

Skill 的核心价值：

- 给 Agent 一套招投标领域的执行规程，而不是给用户一个 UI。
- 约束 Agent 不得把整本标书直接塞进上下文，而必须先解析、切分、检索、引用证据。
- 约束 Agent 不得编造资质、案例、认证、人员、参数或法律结论。
- 让 Agent 在资料不足时主动追问用户，而不是强行判断。
- 让 Agent 输出可复核的审查结果：每个判断都带来源、页码、证据、置信度和人工复核建议。

## 2. Skill 名称与触发条件

建议 Skill 名：`rfp-reviewer`

建议 frontmatter：

```yaml
---
name: "rfp-reviewer"
description: "Reviews RFP/tender documents for compliance risks, deviations, missing evidence, and draft responses. Invoke when users provide bidding documents or ask for RFP review."
---
```

必须触发本 Skill 的用户意图：

- 用户上传或引用招标文件、RFP、采购文件、投标文件、应标文件、偏离表、报价表、资格证明材料。
- 用户要求审查废标风险、无效投标风险、资格/商务/技术符合性。
- 用户要求生成合规偏离表、响应矩阵、补充材料清单、应标初稿。
- 用户要求比对企业资质库、产品白皮书、历史标书、案例库与招标要求。
- 用户要求检查签章、授权、保证金、最高限价、投标有效期、星号项、实质性响应。

不应触发本 Skill 的情况：

- 用户只是问通用招投标法律常识，且没有具体文件需要处理。
- 用户只是写普通商务邮件、销售方案或合同摘要。
- 用户要求做正式法律意见书，且没有授权 Agent 执行文件审查。

## 3. Agent 角色边界

Skill 激活后，Agent 应扮演：

> 招投标合规预审与应标协作助手。

Agent 不能扮演：

- 法院、仲裁机构、行政监督部门。
- 评标委员会或采购代理机构的最终裁判者。
- 律师出具正式法律意见书的替代品。
- 能保证中标或保证不废标的承诺方。

Agent 的输出措辞必须使用：

- “疑似触发风险”
- “建议人工复核”
- “根据当前材料未发现证明”
- “需要用户补充确认”
- “可能构成负偏离/未实质性响应”

Agent 禁止使用：

- “必然废标”
- “一定有效”
- “保证中标”
- “无需人工确认”
- “完全符合法律要求”

## 4. Claude 方案需要保留与修正的部分

### 4.1 可以保留

- “规划-检索-反思-生成”的闭环思路是正确的。
- 资格、形式、商务、技术分阶段审查是合理方向。
- 多格式解析是必要能力。
- 偏离表、补料清单、应标初稿是高价值输出。
- Critic 角色用于二次审查是必要的。

### 4.2 必须修正

- 不能只依据财政部 87 号令。Agent 必须先识别项目类型，再选择规则集。
- 不能直接宣称“模拟评标委员会判废标”。应改为“模拟评审视角风险预审”。
- 不能把 OCR 识别公章/签字作为法律强判定，只能作为线索和置信度提示。
- 不能承诺全格式解析。P0 只覆盖 ZIP、PDF、DOCX、XLSX、PNG、JPG。
- 不能生成无证据的“完全响应”。所有满足判断必须绑定企业资料证据。

## 5. 法规与规则选择策略

Agent 不应把法规写死为单一标准，而应执行规则分流。

### 5.1 政府采购货物与服务

优先参考：

- 《政府采购货物和服务招标投标管理办法》（财政部令第 87 号）。
- 其中第 63 条列举投标无效情形：未按招标文件提交投标保证金、投标文件未按要求签署盖章、不具备资格要求、报价超过预算金额或最高限价、含有采购人不能接受的附加条件等。
- 来源：[国务院公报 - 财政部令第87号](https://www.gov.cn/gongbao/content/2017/content_5241918.htm)。

### 5.2 工程建设项目招标

优先参考：

- 《中华人民共和国招标投标法实施条例》。
- 其中第 51 条列举否决投标情形：未经单位盖章和单位负责人签字、联合体未提交共同投标协议、不符合资格条件、报价低于成本或高于最高投标限价、未响应实质性要求等。
- 来源：[国务院政策文件库 - 招标投标法实施条例](https://www.gov.cn/zhengce/zhengceku/2011-12/29/content_4066.htm)。

### 5.3 电子招投标

优先参考：

- 《电子招标投标办法》。
- 电子投标文件以数据电文形式提交，交易平台涉及加密、解密、拒收未按规定加密文件、电子签名等能力。
- 来源：[国务院 - 电子招标投标办法](https://www.gov.cn/zhengce/2021-11/30/content_5713227.htm)。

### 5.4 政府采购需求管理

优先参考：

- 《政府采购需求管理办法》。
- 其中规定采购需求包括技术要求和商务要求，需求应清楚明了、表述规范、含义准确，量化指标应明确等次。
- 来源：[国务院公报 - 政府采购需求管理办法](https://www.gov.cn/gongbao/content/2021/content_5623061.htm)。

### 5.5 招标文件自身规则优先

Agent 必须记住：

- 招标文件中的投标人须知、资格审查表、符合性审查表、评分办法、废标条款、偏离表模板，是最直接的项目规则。
- 法规是底线和解释依据，项目文件是具体审查标准。
- 如果法规与招标文件理解存在冲突，Agent 应标记“需法务复核”，不得自行给最终结论。

## 6. Skill 执行总流程

Skill 激活后，Agent 必须按以下顺序执行，不得跳步。

### Step 1：确认输入材料

Agent 先识别用户提供了哪些材料：

- 招标文件/RFP/采购文件。
- 投标文件/应标文件草稿。
- 企业资质材料。
- 产品白皮书/技术参数。
- 历史标书/案例材料。
- 偏离表模板。
- 报价表/分项报价。
- 授权书、保证金、签章文件、承诺函。

如果缺少关键材料，Agent 不应立刻审查全部内容，而应先说明限制并追问。

必要追问示例：

- “请确认哪一份是主招标文件？”
- “是否有企业资质库或产品白皮书用于比对？”
- “是否需要我只做招标文件风险抽取，还是同时比对应标文件？”
- “偏离表是否有招标方指定 Excel 模板？”

### Step 2：文件预处理

Agent 应调用本地工具完成文件预处理。

预期工具：

- `file_unpacker.py`：递归解压 ZIP/RAR/7z，生成文件树和文件清单。
- `file_classifier.py`：识别主招标文件、投标文件、资质文件、报价表、偏离表模板。
- `hash_manifest.py`：生成文件哈希和审计清单。

输出：

- 文件树。
- 文件类型。
- 解析状态。
- 无法处理文件清单。
- 需要用户确认的文件。

### Step 3：多格式解析

Agent 根据文件类型调用解析工具。

预期工具：

- `pdf_parser.py`：解析文本型 PDF，保留页码、段落、表格。
- `pdf_ocr_parser.py`：解析扫描 PDF 和图片，输出 OCR 文字、页码、置信度。
- `docx_parser.py`：解析 DOCX 段落、标题、编号、表格、页眉页脚、批注。
- `excel_parser.py`：解析 XLSX sheet、表头、单元格、合并单元格、公式。
- `image_ocr.py`：识别图片证书、有效期、编号、机构、公章线索。

统一输出为 Document AST：

```json
{
  "file_id": "FILE-001",
  "file_name": "招标文件.pdf",
  "elements": [
    {
      "element_id": "E-0001",
      "type": "paragraph",
      "page": 12,
      "section": "投标人须知",
      "text": "投标有效期为90日历天。",
      "bbox": null,
      "confidence": 0.98
    }
  ]
}
```

### Step 4：项目类型与规则集识别

Agent 必须识别项目适用场景：

- 政府采购货物/服务。
- 工程建设招标。
- 国企/央企采购。
- 金融机构采购。
- 普通企业 RFP。
- 电子招投标。

识别依据：

- 招标公告标题。
- 采购人/代理机构。
- 项目编号格式。
- 招标文件引用法规。
- 采购方式和评审办法。
- 是否提到政府采购、财政部门、公共资源交易平台、电子招投标平台。

输出：

```json
{
  "project_type": "government_goods_services",
  "applicable_rules": ["MOF_ORDER_87", "RFP_SPECIFIC_RULES"],
  "confidence": 0.82,
  "need_human_confirm": true
}
```

### Step 5：条款抽取与分类

Agent 从主招标文件中抽取 requirement。

必须抽取的类型：

- 项目信息：项目名称、编号、包号、采购人、代理机构。
- 时间节点：报名、答疑、投标截止、开标、保证金、有效期。
- 资格要求：营业执照、许可、认证、纳税、社保、财务、信用。
- 形式要求：签章、授权、文件格式、正副本、密封、加密、电子签章。
- 商务要求：交付、付款、质保、售后、SLA、培训、驻场、保险。
- 技术要求：功能、性能、接口、安全、协议、兼容性、验收。
- 价格要求：预算、最高限价、报价方式、税率、分项报价。
- 合同风险：违约责任、保密、知识产权、数据安全、赔偿上限。
- 评分办法：评分项、分值、证明材料、客观/主观评分项。
- 否决项：无效投标、废标、实质性不响应、星号项。

强制性识别规则：

- 强制词：必须、须、应当、不得、不接受、无效、否决、不予受理。
- 标记符号：★、☆、▲、重要、核心、实质性。
- 章节位置：资格审查表、符合性审查表、废标条款、投标人须知前附表。
- 表格列名：审查项、证明材料、是否通过、响应要求。

Requirement 输出：

```json
{
  "requirement_id": "REQ-TECH-0021",
  "category": "technical",
  "mandatory_level": "fatal",
  "source_file": "招标文件.pdf",
  "page": 68,
  "section": "技术要求",
  "text": "★系统须支持双活容灾能力。",
  "required_evidence": ["产品白皮书", "技术方案", "架构图"]
}
```

### Step 6：检索企业证据

Agent 不能凭模型记忆判断是否满足，必须检索企业材料。

检索对象：

- 资质库。
- 产品白皮书。
- 技术参数表。
- 历史标书。
- 案例库。
- 人员证书。
- 合同/商务底线。
- 报价和授权材料。

检索策略：

- 关键词检索：适合证书编号、协议名称、型号、金额、日期。
- 向量检索：适合语义相近的技术能力和方案描述。
- 元数据过滤：按产品、行业、有效期、可披露等级过滤。
- rerank：重新排序候选证据，避免只取相似但无效的片段。

证据必须包含：

- 文件名。
- 页码或 sheet/单元格。
- 原文引用。
- 证据类型。
- 有效期。
- 置信度。

### Step 7：合规判定

Agent 应采用四层判定：

1. 规则判定：金额、日期、有效期、是否超限、是否缺文件。
2. 证据判定：是否找到直接证明材料。
3. 语义判定：企业能力描述是否覆盖招标要求。
4. 人工复核：高危或低置信度项必须要求人工确认。

判定结果只能使用这些枚举：

- `满足`
- `不满足`
- `部分满足`
- `存疑`
- `未发现证明材料`
- `不适用`
- `需人工复核`

风险等级只能使用：

- `P0 致命风险`
- `P1 高风险`
- `P2 中风险`
- `P3 低风险`
- `INFO 提示`

判定输出：

```json
{
  "requirement_id": "REQ-TECH-0021",
  "judgement": "存疑",
  "risk_level": "P1 高风险",
  "confidence": 0.62,
  "evidence": [
    {
      "file": "产品白皮书.pdf",
      "page": 23,
      "quote": "支持同城双活部署。"
    }
  ],
  "reason": "白皮书证明产品支持双活，但当前应标方案和报价范围未体现双活部署内容。",
  "human_review_required": true,
  "suggested_action": "补充双活架构图、实施范围和报价说明。"
}
```

### Step 8：生成偏离表

Agent 应生成合规偏离表。

字段建议：

- 条款编号。
- 来源章节/页码。
- 招标要求原文。
- 条款类型。
- 强制等级。
- 我方响应/证明材料。
- 偏离判定。
- 风险等级。
- 证据来源。
- 建议动作。
- 是否需人工确认。

偏离判定建议：

- `正偏离`
- `无偏离/完全响应`
- `负偏离`
- `部分响应`
- `存疑`
- `未响应`

### Step 9：生成补料清单

Agent 必须输出补料清单，尤其是高危和存疑项。

补料类型：

- 需补证书。
- 需更新有效期材料。
- 需签字盖章。
- 需补授权。
- 需补社保/纳税/财务证明。
- 需产品确认。
- 需商务确认。
- 需报价确认。
- 需法务复核。
- 需交付团队确认。

### Step 10：应标草稿生成

Agent 只有在满足以下条件时才能生成应标草稿：

- 条款已抽取。
- 已找到企业证据。
- 判定不是“不满足”。
- 用户明确要求生成应标内容。

生成规则：

- 每段响应必须基于证据。
- 不得把“计划支持”写成“已支持”。
- 不得把“可定制开发”写成“现有功能满足”。
- 不得承诺超出报价、交付、资质或产品范围。
- 对存疑项必须生成“待确认版本”，不能直接写完全响应。

### Step 11：Critic 自审

Agent 在最终输出前必须自审。

自审清单：

- 是否遗漏所有 ★/☆/▲ 项。
- 是否遗漏资格审查表和符合性审查表。
- 是否所有满足项都有证据。
- 是否所有 P0/P1 风险都置顶展示。
- 是否存在无证据生成的资质、案例、参数。
- 是否存在绝对化或过度承诺词。
- 是否存在格式不符合用户要求。
- 是否需要向用户追问。

如果自审失败，Agent 必须修正输出后再回复。

## 7. Agent 追问策略

Agent 不应无脑追问。只有影响审查结论时追问。

必须追问的情况：

- 无法识别主招标文件。
- 缺少企业资质库，但用户要求判断是否满足。
- 缺少产品资料，但用户要求技术响应。
- 缺少报价表，但用户要求检查最高限价或报价风险。
- 缺少偏离表模板，但用户要求按模板填报。
- 发现压缩包加密或文件无法解析。

可以不追问、直接输出限制说明的情况：

- 用户只要求抽取招标要求。
- 用户只要求生成风险初筛。
- 某些证据缺失但不影响整体报告生成。

追问格式：

```text
我可以先做招标文件风险抽取，但要判断我方是否满足，还需要你补充：
- 企业资质材料或资质库目录
- 产品白皮书/技术参数表
- 如需生成偏离表，请提供招标方 Excel 模板
```

## 8. 工具设计计划

Skill 本身不应塞复杂代码。工具应作为 Agent 可调用脚本存在。

建议目录：

```text
.trae/skills/rfp-reviewer/
  SKILL.md
  tools/
    file_unpacker.py
    file_classifier.py
    pdf_parser.py
    pdf_ocr_parser.py
    docx_parser.py
    excel_parser.py
    image_ocr.py
    requirement_extractor.py
    evidence_retriever.py
    compliance_checker.py
    deviation_table_writer.py
    report_writer.py
  schemas/
    source_file.schema.json
    requirement.schema.json
    evidence.schema.json
    judgement.schema.json
    deviation_table.schema.json
  examples/
    sample_manifest.json
    sample_requirements.jsonl
    sample_report.md
```

P0 工具范围：

- `file_unpacker.py`：支持 ZIP，记录不支持/加密文件。
- `pdf_parser.py`：支持文本 PDF。
- `docx_parser.py`：支持 DOCX。
- `excel_parser.py`：支持 XLSX 偏离表和报价表读取。
- `requirement_extractor.py`：抽取条款并分类。
- `compliance_checker.py`：根据证据和规则输出判定。
- `report_writer.py`：输出 Markdown 报告。

P1 工具范围：

- OCR 图片和扫描 PDF。
- Excel 偏离表写回。
- 本地向量索引。
- DOCX 应标草稿导出。

P2 工具范围：

- RAR/7z。
- OFD。
- PDF 数字签名/CA 验证。
- Web 仪表盘或批处理 CLI。

## 9. 输出规范

Agent 最终输出必须包含以下部分。

### 9.1 审查范围说明

说明：

- 已处理文件。
- 未处理文件。
- 是否包含企业证据比对。
- 是否包含应标文件审查。
- 主要限制。

### 9.2 P0/P1 风险置顶

格式：

```markdown
## 高危风险
- 风险：投标有效期疑似不足
- 来源：招标文件第 12 页，要求 90 日历天
- 我方材料：投标函第 3 页，承诺 60 日历天
- 判定：疑似负偏离，P0 致命风险
- 建议：立即修改投标函有效期，并由授权代表重新签署/盖章
```

以 Markdown 表格展示，并可导出 Excel。

### 9.5 应标建议

### 9.6 待人工确认项

## 10. 禁止行为清单

Agent 使用本 Skill 时禁止：

- 直接把整份标书塞进上下文后让模型总结。
- 没有证据就判断“满足”。
- 没有页码/来源就输出关键风险。
- 编造证书、案例、认证、人员、产品参数。
- 把 OCR 低置信度结果当作法律事实。
- 把法规条文编号编错还当作确定依据。
- 忽略招标文件自身的废标条款和审查表。
- 对 P0/P1 风险轻描淡写。
- 在用户未要求时生成完整投标文件。
- 承诺“保证不废标”或“保证中标”。

## 11. 上下文不足的解决方案

Skill 必须明确告诉 Agent：长标书不能靠上下文硬塞。

正确方法：

1. 解析成结构化元素。
2. 抽取成 requirement 列表。
3. 每个 requirement 单独检索证据。
4. 每个 judgement 单独生成理由。
5. 最后汇总风险和偏离表。

Agent 每次处理上下文应只包含：

- 当前条款原文。
- 当前条款上下文摘要。
- 检索到的前 N 条证据。
- 适用规则片段。
- 输出 schema。

## 12. 多格式解析边界

P0 支持：

- `.zip`
- `.pdf` 文本型
- `.docx`
- `.xlsx`
- `.png`
- `.jpg`

P0 不承诺：

- 加密压缩包。
- 电子投标平台专有格式。
- PDF 数字签名法律验证。
- OFD。
- CAD 图纸。
- 复杂扫描件 100% 准确 OCR。

Agent 遇到不支持文件时必须输出：

- 文件名。
- 不支持原因。
- 对审查影响。
- 用户可补充的替代材料。
